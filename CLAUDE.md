# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this package is

`num-fns` is an internationalized number utility library — `date-fns`, but for numbers only. It formats and parses numbers, money and percentages, spells numbers out in words, handles ordinals, short/long notation and roman numerals, and does decimal-safe arithmetic and rounding (`add(0.1, 0.2)` is `0.3`; `src/arithmetic/`, 2026-09-06). Every integer-domain function also takes `number | bigint` and every parser can return a `bigint` via `{ output: 'bigint' }` (`src/shared/bigint.ts`, 2026-09-06 — `todo.md` §4's BigInt item, broadened from `numberToWords`/`toLongNotation` to the whole integer domain).

It was renamed from `az-number-utils`, and the locale refactor (`todo.md` §1) is largely done: `date-fns`-style locale objects live in `num-fns/locale` and are passed per call (`numberToWords(1234, { locale: ru })`), with `az`, `en`, `enGB` (British English, added 2026-08-22 — same vocabulary as `en` plus the British "and": `"one hundred and one"`), `ru` and `es` as the launch locales. **The default locale is `en`, not `az`** — this was an explicit, intentional breaking change (`todo.md` §1's "default locale" decision, 2026-08-09), landed 2026-08-18 alongside the locale-threading itself. Callers that want the pre-refactor behavior pass `{ locale: az }` explicitly; `az` remains fully supported and is the locale every other locale's algorithm is checked against for regressions (`locale/az.test.ts`).

Threaded so far: `numberToWords`, `toOrdinal`/`ordinalToWords`/`getOrdinalSuffix`, `formatNumber`/`parseNumber`, `formatMoney`/`parseMoney`/`moneyToWords` (which also take an ISO 4217 `currency` code — `AZN`/`USD`/`EUR`/`RUB`/`GBP`, defaulting to the locale's own; `enGB` defaults to `GBP`), `formatPercentage`/`parsePercentage`, `toShortNotation`/`parseShortNotation`/`toLongNotation`/`parseLongNotation`, and `numberToDigitWords`. `fractionToWords` takes a `locale` option too, but only `az`, `en` and `enGB` have real fraction-word vocabulary — `ru`/`es` throw rather than guess (see `number/fraction.ts`'s doc comment; `enGB` goes through the generic `Locale.fractions` hook, which it can use because, unlike `en`, it is not `numberToWords`' structural default and so may import from `number/`). `toRoman`/`fromRoman` and `toByteSize`/`parseByteSize` are deliberately locale-independent and don't take the option; financial/stats/arithmetic/utils functions don't either, per `todo.md` §4's "raw numbers" decision.

The pre-existing `locale: 'az' | 'en'` string option on `toShortNotation` has been folded into the full `Locale` object system described above — it now takes a `Locale`, not a bare string.

## Commands

Package manager is Bun.

```sh
bun install                # install dependencies
bun test                   # run the full test suite (bun:test, colocated *.test.ts)
bun test src/number/words.test.ts   # run a single test file
bun test -t "numberToWords"         # run tests matching a name pattern
bun run test:coverage      # the same suite with the coverage gate enforced (what CI runs)
bun run typecheck          # tsc --noEmit, gate before publishing
bun run lint               # biome lint . (biome.json)
bun run lint:fix           # biome lint --write .
bun run format              # biome format --write .
bun run format:check        # biome format .
bun run check                # biome check . (lint + format in one pass)
bun run check:pack           # attw + publint against a packed tarball (run after build)
bun run check:smoke          # install the tarball into real ESM/CJS consumers and run them
bun run build               # vite build -> dist/ (ESM + CJS + per-module .d.ts/.d.cts)
bun run dev                 # vite build --watch
```

Linting and formatting are handled by a single tool, Biome (`biome.json`), not ESLint/Prettier.

`prepublishOnly` runs `check`, the tests, `build`, and finally `check:pack` — that's the full gate before `npm publish`. `check:smoke` is not in `prepublishOnly` (it packs a tarball, which `npm publish` is already in the middle of doing); `ci.yml` and `release.yml` both run it as an explicit step after `check:pack` instead. `check:pack` runs [`attw`](https://github.com/arethetypeswrong/arethetypeswrong.github.io) (`--profile strict`, so **every** resolution mode counts, including legacy `node10`) and `publint --strict` against a packed tarball; it does **not** build, so it needs a `bun run build` ahead of it (both `ci.yml` and `release.yml` order it that way). `check` itself stays build-free and fast.

`bunfig.toml` sets `install.exact = true`, so `bun add`/`bun install` always pin exact versions in `package.json` (no `^`/`~` ranges) — keep that in mind when adding a new dependency.

## Architecture

Each unit (number, money, percentage) has its own directory under `src/`, with a single `format.ts` (or, for the `number/` directory, one file per concern) exporting a `formatX`/`parseX` pair. Everything is re-exported flat from `src/index.ts` — there is no default export and no namespacing, so `formatMoney`, `numberToWords`, `toRoman`, etc. are all imported directly from the package root.

`src/arithmetic/` and `src/utils/` (added 2026-08-09, per the `todo.md` §3 note that these new domains can land as top-level directories regardless of how the `format/`+`parse/` split question resolved — it has since been closed as a rejection, see below) follow the same one-file-per-function convention but hold self-contained helpers with no locale dependency, rather than a `formatX`/`parseX` pair per domain.

**Layout decisions (settled 2026-08-25, `todo.md` §3).** The project vision doc sketches a different tree — top-level `src/{format,parse,humanize,…}/` plus a separate top-level `test/` — and all three divergences were reviewed against this code and deliberately **rejected**. They are not oversights; do not re-propose them.

- **No top-level `test/`.** Tests stay colocated — see "Testing conventions" below for why that is load-bearing rather than stylistic.
- **No `format/` + `parse/` split.** Each domain keeps its formatter and inverse parser in one file (`number/format.ts` 121 lines, `money/format.ts` 55, `percentage/format.ts` 76) because they are written, changed and tested as a unit: money and percentage parsing both delegate to `parseNumber`, their option interfaces sit together in `shared/types.ts`, and the `*.property.test.ts` files assert `parse(format(n)) === n` as one invariant. A split would put both halves of every round trip in different directories and fragment the `number`/`money`/`percentage` grouping callers think in. The vision doc's shape fits a library where formatting and parsing are large independent subsystems; here they are three inverse pairs totalling 252 lines. Note also that internal layout is invisible to consumers — the barrel is a flat `export *` (bar `./number/words`, re-exported by name to keep `resolveScaleWord` internal) and the `exports` map publishes only `.` and `./locale/*` — so a reorg buys no API benefit to weigh against the churn.
- **No `humanize/` directory.** `src/number/` is already almost entirely locale-driven word and scale rendering (`locale` identifiers per module, comments stripped: `words.ts` 23, `notation.ts` 18, `fraction.ts` 11, `suffix.ts` 10, `format.ts` 7, `digits.ts` 5, and `roman.ts`/`byte-size.ts` 0), so a `humanize/` directory would swallow most of it and leave a two-file rump instead of two coherent halves. `notation.ts` also straddles the digits/words line on purpose — `toShortNotation` emits `"1.5M"`, `toLongNotation` emits `"1 million 234 thousand 567"`, and all four functions share one scale table — so it would have to be split across directories or parked arbitrarily. The only real cleavage here is locale-dependent vs. locale-independent, which is not what the vision doc asked for and does not earn a directory for two files.

- `src/number/format.ts` — `formatNumber` / `parseNumber`, the base formatter every other formatter (money, percentage) delegates to for grouping digits and joining the fractional part. Defaults come from `options.locale.formatDefaults` (`en`: comma thousands separator, period decimal separator); an explicit `thousandsSeparator`/`decimalSeparator` always wins. Rounding to `decimals` delegates to `arithmetic/round` (2026-09-06) rather than `toFixed`/`Math.round`, so it is decimal-safe in every `roundingMode`: `formatNumber(1.005, { decimals: 2 })` is `"1.01"` (it was `"1.00"` via `toFixed`), and a non-integer `decimals` now throws `RangeError`. `toFixed` is still used afterwards, only to pad the already-rounded value to `decimals` digits, which is lossless. A `bigint` value takes a separate `splitBigInt` path (2026-09-06): its digits are grouped from `String(value)` at any magnitude, `decimals` only zero-pads (there is nothing to round, so `roundingMode` is ignored) but is validated identically, and `parseNumber(text, { output: 'bigint' })` reads the normalised text exactly through `shared/bigint.ts`'s `decimalToBigInt` — `"1,234.00"` is `1234n`, `"1.5"` throws `RangeError`. The return type follows `output` through three overloads (`'bigint'` → `bigint`, `'number'`/omitted → `number`, unresolved `ParseOutput` → the union); every other parser copies that overload shape.
- `src/number/words.ts` — `numberToWords`, the locale-generic word-composition engine every locale's cardinal reading runs through. Groups a number into base-1000 chunks, renders each chunk's own 0-999 reading via `locale.words.renderGroup` (locale-owned: hyphenation for `en`, the veinti-contraction and "y" for `es`, gender-neutral masculine forms for `ru`, the original hardcoded logic for `az`), resolves each chunk's scale word via `locale.plural` + `locale.words.scales`, and joins chunks via `locale.words.compose` (locale-owned: dropping "bir" before Azerbaijani "min", Russian gender agreement, Spanish "cien"/apocopation). `az`'s `renderGroup`/`compose` are verified byte-identical to the pre-refactor hardcoded implementation (`locale/az.test.ts`, `number/words.test.ts`). The module holds no vocabulary of its own: `ONES`/`TENS`/`SCALE_WORDS`/etc. moved into `locale/az.ts` on 2026-08-25 (`todo.md` §3), so the only export beside `numberToWords` is `resolveScaleWord`, which `number/notation.ts` shares. `resolveScaleWord` is internal: `src/index.ts` re-exports this module by name (`export { numberToWords }`) rather than with `export *`, the one place the barrel is not flat (2026-09-01). A `bigint` goes through `bigIntToWords` (2026-09-06): the same three-step algorithm on groups produced by `shared/bigint.ts`'s `toThousandGroups` in exact integer arithmetic, with the `1000 ** scales.length - 1` cap checked via `maxSupportedBigInt` rather than through a `number` that could not hold a custom locale's larger scales — the locale hooks (`renderGroup`, `plural`, `compose`) still receive plain 0–999 numbers, so no locale has to know.
- `src/number/suffix.ts` — `getOrdinalSuffix` / `ordinalToWords` / `toOrdinal` delegate to `locale.ordinal.suffix`/`locale.ordinal.words`, which each locale implements itself (Azerbaijani vowel harmony lives in `locale/az.ts` now, not here — see that file's doc comment for why it moved). `toOrdinal`'s separator is part of its options object now, not a positional second parameter, to make room for `locale` alongside it. All three (and `withSuffix`) accept a `bigint`, but the ordinal hooks take a `number` (`LocaleOrdinal.suffix`/`words` in `locale/types.ts`), so `getOrdinalSuffix`/`ordinalToWords` narrow it with `shared/bigint.ts`'s `toSafeNumber` and throw `RangeError` above `Number.MAX_SAFE_INTEGER` rather than reaching the hook rounded; `toOrdinal`/`withSuffix` render the digits themselves exactly.
- `src/number/notation.ts` — `toShortNotation`/`parseShortNotation` (scaled abbreviation, e.g. `"2.5M"` default, or `"2,5 mln"` with `{ locale: az }`) and `toLongNotation`/`parseLongNotation` (digit groups paired with scale words, e.g. `"1 million 234 thousand 567"`), both reading `locale.notation.scales`/`locale.words.scales`. Distinct from `numberToWords`: notation functions keep digits and only localize the scale word, they don't spell every number out. `toShortNotation`'s `locale` option used to be a bare `'az' | 'en'` string, unrelated to the `Locale` objects; it's now a real `Locale`. All four take or return `bigint` (2026-09-06): `toShortNotation` divides a `bigint` by the threshold with `scaleBigInt` (exact half-up on the true remainder, standing in for `toFixed`) so a value past the largest scale keeps every digit (`"1500T"`, not `"1.5e15"`); `toLongNotation` chunks it with `toThousandGroups` under the exactly-computed cap; `parseShortNotation` with `output: 'bigint'` multiplies the mantissa by the threshold in decimal (`"2.5M"` → `2500000n`, `"1.2345K"` → `RangeError`); and `parseLongNotation` accumulates its total in `bigint` **whatever the `output`**, so a `number` result is either exact or a `RangeError` pointing at `output: 'bigint'` — it never returns a rounded `number` for a string past `Number.MAX_SAFE_INTEGER` any more (the one behaviour change the feature shipped as breaking; `utils/base.ts`'s `fromBase` got the same treatment).
- `src/number/roman.ts` — standard `toRoman` / `fromRoman`, integers 1–3999 only, self-contained (no dependency on the words/notation modules, and no `locale` option — roman numerals are locale-independent).
- `src/number/digits.ts` — `numberToDigitWords`, digit-by-digit reading (phone numbers, codes), reads `locale.words.zero`/`ones`/`negative`. Takes `number | string | bigint`; a `bigint` is read from `String(value)`, every digit at any magnitude, which a `number` past `Number.MAX_SAFE_INTEGER` cannot promise.
- `src/number/fraction.ts` — `fractionToWords`, only `az` and `en` implemented (see the module's doc comment for why `ru`/`es` throw instead of guessing at fraction-noun vocabulary). `en`'s composer lives in this module rather than as a `Locale.fractions` hook because it needs `numberToWords`, and `en` can't import back from `number/` without a cycle (see `Locale.fractions`'s doc comment in `locale/types.ts`).
- `src/money/currency.ts` — the ISO 4217 registry (2026-09-06, `todo.md` §4's multi-currency item): `CurrencyCode` (`'AZN' | 'USD' | 'EUR' | 'RUB' | 'GBP'`, a closed union so a typo is a compile error), `Currency` (`code`/`symbol`/`decimals`) and `getCurrency(code)`, which throws `RangeError` for anything else. It holds only what is a fact about the *currency* rather than the *language* — the symbol and minor-unit exponent. Symbol placement and the unit words live in each locale's `currency` block (`Locale.currency`: default `code`, `symbolPosition`, and `units` keyed by code — every launch locale covers every code, pinned by the conformance suite). The module imports nothing, so `locale/types.ts` can `import type { CurrencyCode }` from it without a cycle; `locale/types.ts` re-exports the type so a custom locale can be typed from `num-fns/locale` alone. Adding a code means adding it to the union and registry *and* to every locale's `units` — the conformance suite fails otherwise.
- `src/money/format.ts`, `src/percentage/format.ts` — thin wrappers around `formatNumber`/`parseNumber` that add a currency symbol or `%` sign. Money resolves `currency` (default `locale.currency.code`) through `getCurrency` for the symbol and default `decimals`, and takes `symbolPosition` and separators from the locale (`en`: `$` before the amount; `{ locale: az, currency: 'USD' }` → `"9,99 $"`). An explicit `symbol` still wins. Both inherit `formatNumber`'s decimal-safe rounding by delegation; percentage's `multiplyBy100`/`asRatio` scaling additionally goes through `arithmetic/multiply`/`divide` (2026-09-06) instead of `* 100`/`/ 100`, so `formatPercentage(1.005, { multiplyBy100: true })` is `"101%"` (it was `"100%"`, because `1.005 * 100` is `100.49999999999999`). Both take `number | bigint` and both parsers take `output` by inheriting `NumberFormatOptions`/`NumberParseOptions` (2026-09-06): `formatMoney(bigint)` is a whole amount of major units padded to the currency's `decimals`, `parseMoney("$ 1.50", { output: 'bigint' })` throws (the fifty cents cannot be carried), and `parsePercentage` with `asRatio` + `output: 'bigint'` throws for the same reason unless the ratio happens to be whole.
- `src/money/words.ts` — `moneyToWords`, resolves the major/minor unit word for the amount's plural category via `locale.plural` + `locale.currency.units[currency]`'s `plurals` maps (real payoff for `ru`: `"один рубль"`/`"два рубля"`/`"пять рублей"` and `"два доллара"` come out correct without the caller doing anything), and spells the amount in the unit's `gender` (`es` + GBP: `"una libra"`). Throws `RangeError` when the locale has no `units` entry for the code — it never borrows another language's words. A `bigint` amount (2026-09-06) is a whole number of major units read exactly by `numberToWords`' `bigint` path, minor part zero (spelled only with `includeZeroMinor`); the plural category comes from `shared/bigint.ts`'s `pluralOperand`, so `moneyToWords(2n, { locale: ru })` is still `"два рубля"` and `Locale.plural` never sees a `bigint`.
- `src/shared/types.ts` — shared option interfaces; every one that has a locale-dependent default now carries an optional `locale?: Locale` field (defaulting to `en` at the call site, not here — this file only declares the shape). It also owns the `RoundingMode` union (`'halfUp' | 'halfDown' | 'halfEven' | 'ceil' | 'floor'`), shared by `NumberFormatOptions.roundingMode` and `arithmetic/round`'s `mode` parameter — one vocabulary, one implementation (see the `src/arithmetic/` entry below). The type stays here rather than moving into `arithmetic/` because the formatters' option interfaces reference it and `arithmetic/round` should not import from a formatter. It likewise owns `ParseOutput` (`'number' | 'bigint'`) and the `ParseOutputOptions { output? }` mixin (2026-09-06) that `NumberParseOptions` (hence money/percentage), `ShortNotationParseOptions`, `LongNotationParseOptions` (new — `toLongNotation`'s options plus `output`), `ByteSizeParseOptions` and `BaseParseOptions` (`fromBase`'s trailing options, only `output`) extend; its doc comment is the one place the whole-number rule and the unsafe-`number` `RangeError` are spelled out for consumers.
- `src/shared/` — `types.ts` (shared option interfaces), `validation.ts` (internal guards) and `bigint.ts` (internal `bigint` plumbing, below). There is no `constants.ts`: it held `DEFAULT_THOUSANDS_SEPARATOR`/`DEFAULT_DECIMAL_SEPARATOR`/`AZN_SYMBOL`, which were Azerbaijani values (`' '`, `','`, `₼`) that only `locale/az.ts` read, and which the `DEFAULT_` prefix made look like package-wide fallbacks — every function actually falls back to `en`. They are private to `locale/az.ts` now (2026-08-25, `todo.md` §3).
- `src/shared/bigint.ts` — the internal `bigint` helpers behind both halves of the BigInt support (2026-09-06, `todo.md` §4's "BigInt input path" item, broadened to every integer-domain function and every parser). Not exported from the root, like `validation.ts` and `arithmetic/decimal.ts`; consumers see only the `number | bigint` parameter types and the `output` option. Input side: `toThousandGroups` (base-1000 chunking for either type — the `number` branch is the loop `numberToWords`/`toLongNotation` always ran, the `bigint` branch its exact twin), `maxSupportedBigInt` (the `1000^n - 1` cap computed exactly), `scaleBigInt` (divide-and-render with exact half-up rounding, the `bigint` stand-in for `(value / threshold).toFixed(decimals)` in `toShortNotation`/`toByteSize`), `absBigInt`, `pow10`, and the `ZERO`/`ONE`/`THOUSAND` constants. Output side: `decimalToBigInt` (the one string-to-`bigint` conversion; reads sign, fraction and exponent exactly, returns `null` for non-decimal text so the caller raises its own `SyntaxError`, throws `RangeError` when the value is not a whole number), `scaledBigInt` (mantissa × factor for the scaled parsers), `resolveOutput` (validates the `output` option — anything but `'number'`/`'bigint'`/omitted is a `RangeError`), `toOutput` + `assertSafeInteger` (convert an exact result to the requested type, refusing to hand back an unsafe `number`). Locale boundary: `pluralOperand` folds a `bigint` beyond the safe range to its last six digits plus a million (every CLDR integer plural rule is invariant under that) so `Locale.plural` keeps its `number` signature, and `toSafeNumber` narrows for the `number`-only ordinal hooks or throws. `BigInt` is reached only through the `BigInt(...)` constructor, never `10n` literals — same ES2018 reason as `arithmetic/decimal.ts`.
- `src/locale/types.ts` — the `Locale` interface itself. `LocaleWords.renderGroup` (a locale's own 0-999 word composer) and `LocaleWords.decimalConnector` (the integer/fraction joiner — split out from the overloaded `and` field, which is now solely the intra-group tens+ones connector, e.g. Spanish `'y'`) were added as part of the locale-threading work; see their doc comments for why. As of 2026-08-22 every locale sets `decimalConnector`: `az` `'tam'`, `en`/`enGB` `'point'`, `ru` `'запятая'`, `es` `'coma'`. `LocaleCurrencyUnit.gender` (2026-08-22) lets a currency unit pick the grammatical gender `moneyToWords` spells its amount with (`ru`'s feminine `копейка` → `"одна копейка"`); set it only on locales that declare `words.genders`. `LocaleCurrency` was reshaped on 2026-09-06 from one `symbol`/`major`/`minor` triple into `code` + `symbolPosition` + `units` (a per-`CurrencyCode` map of `{ major, minor }`), with the symbol moving to `money/currency.ts`'s registry — see that module's entry above. The BigInt work (2026-09-06) changed **no** signature here on purpose: `plural`, `ordinal.suffix`/`ordinal.words` and `words.renderGroup` still take a `number`, and their doc comments say how a `bigint` is kept away from them (`pluralOperand`/`toSafeNumber` in `shared/bigint.ts`), so a custom locale written against 0.3.0 needs no update.
- `src/arithmetic/` — the "precise arithmetic" domain (`todo.md` §4). `clamp.ts`/`in-range.ts` (2026-08-09) are the plain range helpers: `clamp` and `inRange`, both inclusive `[min, max]`, both throwing `RangeError` on non-finite input or `min > max`. `add.ts`/`subtract.ts`/`multiply.ts`/`divide.ts`/`round.ts` (2026-09-06) are the decimal-safe operations, and `decimal.ts` is the internal plumbing they share — not exported from the root, so a consumer sees five functions that take and return plain numbers (`todo.md` §4's "raw numbers" decision; no decimal type, no bignum dependency). The design: every finite number is read at its shortest decimal string (`String(0.1)` is `"0.1"`, which is what the caller *means*), decomposed by `toDecimal` into an integer `digits` and a power-of-ten `scale` (`value = digits × 10^-scale`), operated on exactly with `BigInt`, and converted back by `fromDecimal` through `Number("<digits>e<-scale>")` — string-to-number conversion is correctly rounded by the language, whereas `Number(digits) / 10 ** scale` would round twice. `BigInt` is used only through the `BigInt(...)` constructor, never `10n` literals: the build targets ES2018 (`vite.config.ts`, `tsconfig.json`), where the literal syntax is a parse error but the global is a plain runtime value on every supported Node. `divide` shifts the dividend so the integer quotient carries 25 significant digits before conversion (`QUOTIENT_DIGITS`) — exact when the quotient terminates (`divide(0.3, 0.1)` is `3`), otherwise the same as correctly rounding the true quotient (`divide(1, 3)` is `0.3333333333333333`). `round(value, precision = 0, mode: RoundingMode = 'halfUp')` is **the one rounding implementation in the package**: `formatNumber` (hence `formatMoney`) delegates to it and `formatPercentage`'s scaling uses `multiply`/`divide`, so `round(1.005, 2)` and `formatNumber(1.005, { decimals: 2 })` agree on `1.01`. It accepts a negative `precision` (`round(1234, -2)` is `1200`), handles the tie modes on the exact dropped digits (`round(2.5, 0, 'halfEven')` is `2`, `round(-2.5, 0, 'halfDown')` is `-2`) and `ceil`/`floor` directionally (`round(-1.21, 1, 'floor')` is `-1.3`). All five throw `RangeError` on non-finite input, division by zero, a non-integer `precision`, or a result outside the range of a JavaScript number (a "precise" function never hands back `Infinity`), and never return `-0`.
- `src/utils/base.ts` — `toBase`/`fromBase`, arbitrary-radix (2–36) conversion, distinct from the locale digit-system conversion planned in `todo.md` §1 (Latin ↔ Arabic-Indic *within* base 10 — this is base-10 ↔ base-N). `toBase` takes `number | bigint` (a `bigint` converts exactly at any magnitude via `toString(radix)`); `fromBase(value, radix, { output })` accumulates exactly and, like `parseLongNotation`, throws `RangeError` pointing at `output: 'bigint'` rather than returning a rounded `number` for a string past `Number.MAX_SAFE_INTEGER` (2026-09-06).
- `src/utils/predicates.ts` — `isEven`/`isOdd`, throwing `TypeError` for non-integers; both take `number | bigint`, since a `bigint` is where parity of a large id stops being answerable with a `number` (`isEven(BigInt('9007199254740993'))` is `false`, the `number` would have rounded to an even value). `isInteger` was deliberately not added — it would just rename `Number.isInteger`.

All public functions validate input up front and throw (`RangeError`/`TypeError`/`SyntaxError`) rather than returning `NaN`/`undefined` on bad input (non-finite numbers, out-of-range roman numerals, unparseable strings). **This covers option combinations, not just values** (2026-09-01, `todo.md` §4): `formatNumber`/`parseNumber` throw `RangeError` when `thousandsSeparator === decimalSeparator` — the pair that used to make `parseNumber('0.001', { thousandsSeparator: '.', decimalSeparator: '.' })` return `1` — and `toLongNotation`/`parseLongNotation` throw when `groupSeparator` is empty or contains a digit, which used to emit the unparseable `"1 million234 thousand"`. Both guards live in `shared/validation.ts` (`assertDistinctSeparators`, `assertGroupSeparator`) so the money and percentage formatters inherit them by delegation. **It also covers numeric type** (2026-09-06, the BigInt item): a `bigint` argument never passes through a float anywhere in the package — it is chunked, scaled and grouped in integer arithmetic, and where a `number`-only locale hook has to be reached (`ordinal.*`) the narrowing throws `RangeError` beyond `Number.MAX_SAFE_INTEGER` instead of rounding — and a parser never hands back a `number` it knows to be inexact: `output: 'bigint'` demands a whole number (`"1.5"` → `RangeError`), and a parser that computes exactly (`parseLongNotation`, `fromBase`) refuses to return a rounded `number` for a value past the safe range, pointing the caller at `output: 'bigint'`. A `bigint` is never silently `Number()`-converted, and a fraction is never silently truncated into a `bigint`.

### Build output

`vite.config.ts` builds `src/index.ts` in library mode to both `dist/index.js` (ESM) and `dist/index.cjs` (CJS), targeting `es2018` for compatibility with older consumers, with `vite-plugin-dts` emitting per-module `.d.ts` files (not rolled up into one file — rollup-based type bundling pulls in `@microsoft/api-extractor`, which was unreliable in this environment, so `rollupTypes` is intentionally left off). `build.emptyOutDir` is set to `false`; the `dist/` directory is not cleaned before each build.

`vite-plugin-dts` emits extensionless relative specifiers (`export * from './arithmetic/clamp'`), which `node16`/`nodenext` resolution rejects, and emits only `.d.ts` files — which, with `"type": "module"`, means CJS consumers of `dist/index.cjs` were handed ESM types (attw's `FalseESM`). `scripts/fix-dist-types.ts` fixes both: it rewrites each `.d.ts` in place with explicit `.js` extensions and writes a `.d.cts` twin with `.cjs` extensions, so `exports[...].require.types` points at real CJS declarations. It is idempotent, which matters because `emptyOutDir` is `false`, and it throws rather than guessing when a specifier matches neither `<base>.d.ts` nor `<base>/index.d.ts` (a stale declaration from a deleted module is the usual cause — remove `dist/` and rebuild).

It is invoked from the dts plugin's `afterBuild` hook in `vite.config.ts`, not as a separate step chained onto `build`, so `vite build --watch` (`bun run dev`) produces correct declarations too. Running the file directly (`bun scripts/fix-dist-types.ts`) is the manual escape hatch.

Every `exports` entry therefore has per-condition `types` — `import` → `.d.ts`, `require` → `.d.cts` — and `bun run check:pack` (attw `--profile strict` + `publint --strict`) is the regression test.

Legacy `node10` resolution **is** supported, as of 2026-08-21. It cannot read `exports` at all, so the six subpaths (`./locale` and `./locale/{az,en,en-gb,ru,es}`) resolve through `typesVersions` in `package.json` instead — that field exists for no other reason, and it must be kept in sync with `exports` and `vite.config.ts`'s entry list whenever a subpath is added. With it in place attw passes under its default `strict` profile with nothing ignored; the `--profile node16` flag that used to skip the `node10` row is gone. `scripts/smoke/types-node10/` is the regression test: a consumer with `moduleResolution: node10` that imports every subpath and typechecks. Removing `typesVersions` makes it fail with `TS2307 Cannot find module 'num-fns/locale/az'` — verified, not assumed.

That fixture runs on `@typescript/typescript6`'s `tsc6` binary rather than the pinned `typescript` (7.x), because TypeScript 7 **removed** `moduleResolution: node10` (`error TS5108`) and 6 only accepts it behind `"ignoreDeprecations": "6.0"`. So `typesVersions` serves consumers still on TypeScript 5.x/6.x with legacy resolution; anyone on 7 has no legacy mode left to be broken by.

The export map declares `.`, `./locale`, `./locale/{az,en,en-gb,ru,es}` and `./package.json`, one per Vite entry in `vite.config.ts` — adding a subpath means adding both, in both files.

### Testing conventions

Tests are colocated as `*.test.ts` next to the module they cover and use `bun:test` (`describe`/`it`/`expect`) — no separate `tests/` directory, no Vitest/Jest. Every module has a matching test file. **This is a settled decision, not an accident** (`todo.md` §3, 2026-08-25): the project vision doc lists a top-level `test/`, and it was considered and rejected. Colocation is load-bearing — the `src/**/*.test.ts` glob is what keeps test files out of the bundle and out of the emitted declarations (`vite.config.ts`'s dts `exclude`, `tsconfig.build.json`), `knip.json`'s project globs assume it, `scripts/new-function.ts` scaffolds the colocated pair, `src/shared/arbitraries.test.ts` carries a `.test.ts` name *specifically* to inherit those excludes (which only works inside `src/`), and the per-file coverage gate leans on every module having a visible test neighbour. Moving 47 files into a mirror tree would rewrite every relative import and buy nothing: this package has no fixtures, no e2e layer and no separate test build. When adding a new exported function, the existing test files show the expected pattern: cover the documented default behavior, at least one option override, and the thrown-error cases.

Three additions to that baseline, all added 2026-08-20:

- **Property tests** live in `*.property.test.ts` beside the example-based file (`number/format.property.test.ts` next to `number/format.test.ts`, and so on) and use [`fast-check`](https://fast-check.dev). They cover every format/parse pair across all five locales — the point is the invariant (parsing a formatted number returns the number) rather than specific strings, since all three separator conventions (`,`/`.`, ` `/`,`, `.`/`,`) run through the same code. The lossy formatters (`toByteSize`, `toShortNotation`) assert a *bounded* round trip, not an exact one. Shared arbitraries are in `src/shared/arbitraries.test.ts` — named `.test.ts` deliberately, so the Vite build and `vite-plugin-dts` both skip it via the existing `src/**/*.test.ts` exclude; it builds decimals out of integer parts rather than using `fc.double`, so generated values always have a plain-digit `String()` form (a precondition of every round trip here, since `formatNumber` groups digit characters).
- **The coverage gate** is `bunfig.toml`'s `[test].coverageThreshold`, set to **100% per file** and enforced by `bun run test:coverage`. Read that file's comment before touching it: bun 1.3.13 silently ignores the documented per-metric table form, so the threshold is the scalar form, which applies per file; and per-file thresholds only see files a test actually loads, which is why `src/index.test.ts` and `src/locale/index.test.ts` import every module through the barrels. A line that looks impossible to cover means the guard is in the wrong place — `locale/az.ts` had two copies of the same vowel scan and only one was reachable, so they were merged into `lastVowel(word, context)` rather than the gate being loosened.
- **`src/index.test.ts` pins the public export surface** as an explicit sorted list (51 entries today, all of them functions — `getCurrency` joined on 2026-09-06, and `add`/`subtract`/`multiply`/`divide`/`round` the same day, 46 → 51). Adding an `export *` to `src/index.ts` without updating that list fails the suite on purpose — everything in it becomes semver-locked at 1.0. The eleven Azerbaijani vocabulary constants that used to sit in it were removed on 2026-08-25, and `resolveScaleWord` on 2026-09-01 (`todo.md` §3) — the latter by switching `./number/words` to a named re-export, so `export *` is now the rule for every module in the barrel except that one. `money/currency.ts` keeps its `CURRENCIES` table module-private for the same reason: the only runtime export is `getCurrency`, so the root stays functions-only. `arithmetic/decimal.ts` is likewise not in the barrel at all — its `Decimal` interface and `toDecimal`/`fromDecimal`/`alignScales`/`pow10`/`digitCount` helpers are internal, and only the five operation modules are re-exported. `shared/bigint.ts` (2026-09-06) is in the same position: the BigInt input/output support added **no** root export — the list is still 51 — because it surfaces as widened parameter types (`number | bigint`) and an `output` option on existing functions, not as new ones; `ParseOutput`/`ParseOutputOptions`/`LongNotationParseOptions`/`BaseParseOptions` are types, which the runtime list does not see.

The consumer-side smoke fixtures under `scripts/smoke/` are *not* part of this suite: they are separate throwaway projects that install the packed tarball (see `scripts/smoke.mjs`), and `tsconfig.json`/`knip.json` both exclude them for that reason.
